# نظام المحاسبة — دليل البرنامج والتشغيل

يوضح هذا الدليل تطبيق Flutter الحالي، وطريقة عمل شاشاته وخدماته، وعلاقته
بالنظام القديم `CodesSystem`. ويميز بين الوظائف الموجودة فعلياً وبين أعمال
الترحيل التي لم تُربط بعد. أسماء النماذج والقوائم والجداول والأعمدة والفهارس
والقيم المخزنة في النظام القديم هي أسماء توافقية؛ يجب المحافظة على كتابتها
وحروفها كما هي.

## 1. تعريف النظام وبنية المستودع

المشروع هو إعادة كتابة متعددة المنصات لنظام المحاسبة المالية القديم. النظام
السابق يعمل على Windows باستخدام VB.NET وWinForms وقاعدة Microsoft Access.
يحتفظ هذا المستودع بتطبيق المحاسبة المكتوب بـFlutter ويضيف أساساً للترحيل
يحافظ على أسماء النظام القديم وبياناته، مع إتاحة التشغيل على الحاسوب والويب.

يحتوي المستودع القديم على عائلات برامج متعددة. توجد الواجهة ونماذج WinForms في
`WindowsApp1`، ونحو 355 ملف نموذج بيانات VB.NET في `DAL`، ومشروعات للتقارير
وقوالب الطباعة، وتكامل ZATCA، وأدوات استيراد وتصدير قواعد البيانات. يصف ملف
المخطط المرفق 357 جدولاً و982 فهرساً. لا يحتوي المخطط على تعريفات للعلاقات
الخارجية؛ لذلك يجب تأكيد العلاقات من سلوك النظام أو من قاعدة البيانات الأصلية
بدلاً من تخمينها اعتماداً على تشابه الأسماء.

تشمل عائلات البرامج القديمة: المحاسبة العامة وإدارة المتجر، إدارة الأملاك،
الوحدات السكنية المفروشة، الخدمات العامة، المطاعم والمطابخ، المقاولات، شؤون
الموظفين، تأجير العمال، المعارض والمستودعات، النظام الإداري الشامل، الجمعيات
الخيرية، النظافة، قطع الغيار، المصانع، الجمعيات الاستثمارية، الاستراحات،
مغاسل الملابس، المشاغل النسائية، والخياطة والزي الموحد. تطبيق Flutter الحالي
هو أساس المحاسبة، ولا يعني وجود هذه العائلات في النظام القديم أنها أُعيدت
كتابتها بالفعل.

## 3. تشغيل البرنامج

### 3.1 المتصفح أو معاينة Replit

يقوم مسار تشغيل المحاسبة بإعداد ملفات SQLite WebAssembly ثم بناء نسخة Flutter
للويب وخدمتها. من جذر المستودع يمكن استخدام:

```sh
pnpm install --frozen-lockfile
pnpm --filter @workspace/accounting run build
pnpm --filter @workspace/accounting run serve
```

يقوم سير العمل في Replit بالبناء والتشغيل وفق الأمر المسجل له. خادم API مسار
منفصل:

```sh
pnpm --filter @workspace/api-server run dev
```

يوفر API حالياً مسارات المصادقة والتحقق من الصلاحيات. أما شاشات العمل في
المتصفح فتستخدم تخزيناً محلياً متوافقاً مع SQLite، عبر SQLite WebAssembly
وتخزين المتصفح. لم تُربط بعد بالجداول العلائقية القديمة المتحقق منها على خادم
مشترك.

### 3.2 مشغل الحاسوب

شغّل تطبيق Flutter من:
`artifacts/accounting/flutter_app`. عند تشغيل تطبيق سطح المكتب بشكل عادي تظهر
شاشة اختيار بين وضعين:

1. **تطبيق سطح المكتب المستقل:** يفتح واجهة المحاسبة مباشرة، ويبدأ قاعدة
   البيانات المحلية ورفيق الطباعة. هذا الوضع مصمم للعمل محلياً ولا يحتاج إلى
   Node.js.
2. **واجهة ويب محلية في المتصفح:** تطلب مجلد نسخة المشروع الكاملة، وتتحقق من
   Node.js وpnpm وFlutter وإعدادات البيئة والمنافذ المطلوبة، ثم تثبت التبعيات
   المطابقة للقفل، وتبني API والواجهة، وتبدأ خدمة الطباعة وخادم API وخادم
   الويب، ثم تفتح المتصفح.

يتطلب كود تشغيل رفيق الويب حالياً وجود `DATABASE_URL` محلي لقاعدة PostgreSQL
في ملف `.env` داخل نسخة المشروع. لم تُربط مسارات بيانات الأعمال في API بمخطط
SQL القديم بعد؛ لذلك لا يعني هذا الشرط أن مزامنة بيانات الأعمال عبر الإنترنت
أصبحت جاهزة. لا ترفع ملف `.env` أو كلمات المرور إلى Git.

أوامر شائعة للمطور، من جذر المستودع:

```sh
cd artifacts/accounting/flutter_app
flutter pub get --enforce-lockfile
flutter run -d macos
flutter build macos
```

يمكن استبدال `macos` بهدف Flutter متاح مثل `windows` أو `linux`. استخدم
`flutter doctor` إذا لم تكن أدوات المنصة الأصلية مثبتة. التشغيل العادي يعرض
شاشة اختيار الوضع؛ أما أعلام البناء فتُستخدم لأوضاع الرفيق والخدمات الخاصة.

يحتاج وضع الويب إلى مجلد `Codes_System` كاملاً لأنه يستخدم ملف القفل والسكربتات
وAPI وبناء Flutter الموجودة فيه. يتذكر المشغل المجلد المختار على ذلك الجهاز.
استخدم زري التشغيل والإيقاف في الرفيق بدلاً من إنهاء عمليات الخوادم التابعة
يدوياً.

## 4. تسجيل الدخول والأدوار والصلاحيات

تعرض شاشة الدخول أربعة أدوار:

- `admin`
- `cashier1`
- `cashier2`
- `auditor`

في الويب، ترسل المصادقة الطلب إلى `/api/auth/login`، ويستعلم التطبيق من API
للتحقق من صلاحية الإجراءات المحمية. أما تطبيق سطح المكتب المستقل فيستخدم
مخزناً محلياً آمناً للمصادقة. يستطيع رفيق الويب إدارة كلمات مرور الأدوار بعد
التحقق من كلمة مرور المسؤول. توجد متطلبات حد أدنى لطول كلمات المرور الجديدة.

مصفوفة الصلاحيات المستخدمة حالياً:

| الصلاحية | المسؤول | الكاشير 1 | الكاشير 2 | المدقق |
| --- | :---: | :---: | :---: | :---: |
| عرض المخزون والحسابات | نعم | نعم | نعم | نعم |
| إدارة الأصناف أو الحسابات أو حذفها | نعم | لا | لا | لا |
| عرض الفواتير وحفظها | نعم | نعم | نعم | عرض فقط |
| طباعة الفواتير | نعم | نعم | لا | نعم |
| تطبيق خصم على الفاتورة | نعم | نعم | لا | لا |
| اعتماد/إرسال الفاتورة | صلاحية المسؤول موجودة؛ الإجراء غير مكتمل |
| عرض الباركود وطباعته | نعم | نعم | نعم | نعم |
| إدارة المستخدمين والطابعات والنسخ الاحتياطية | نعم | لا | لا | لا |

تُفحص الصلاحيات في واجهة Flutter وفي نقطة التحقق في API. يتطلب التشغيل
الإنتاجي مفتاح توقيع للجلسات وكلمات مرور للأدوار. لا تستخدم بيانات التطوير
الافتراضية في الإنتاج. خزّن إعدادات النشر في أداة الأسرار الخاصة بالبيئة أو
في ملف محلي خاص، ولا تضعها داخل ملفات المصدر.

### إعدادات التشغيل

| الإعداد | الاستخدام |
| --- | --- |
| `SESSION_SECRET` | توقيع جلسات API؛ وهو مطلوب لتسجيل الدخول والتحقق من الصلاحيات. |
| `ACCOUNTING_ROLE_PASSWORDS` | كائن JSON يحتوي كلمات مرور الأدوار الأربعة. استخدم كلمات مرور قوية في الإنتاج. |
| `DATABASE_URL` | يشترطه رفيق الويب المحلي حالياً لتشغيل بيئة العمل المرتبطة بـPostgreSQL؛ لم تُربط به جداول الأعمال القديمة بعد. |
| `PRINTER_ALLOWED_ORIGINS` | أصول المتصفح المسموح لها باستخدام خدمة الطباعة المحلية، مفصولة بفواصل. |

يحفظ رفيق الويب المحلي إعداد كلمات المرور ومفتاح الجلسات الذي ينشئه أو
يحدّثه في مخزن محلي آمن، ثم يعيد تشغيل API بعد تغيير كلمة المرور. لا تضع هذه
القيم في بلاغ عام أو صورة شاشة أو ملف `.env` مرفوع إلى Git.

## 5. النافذة الرئيسية والتنقل

تتكون النافذة الرئيسية من:

- قائمة علوية منسدلة للشاشة الرئيسية والإدارة والأدوات والأصناف.
- شريط أزرار للأقسام الرئيسية: الفواتير والباركود والحسابات والمخزون
  واعتماد الفواتير، إضافة إلى التحديث والموقع واللغة والخروج والآلة الحاسبة.
- مساحة محتوى؛ وتعني الخلفية الزرقاء أن لا نموذج مفتوح حالياً.
- شريط حالة في الأسفل.

تُفتح النماذج فوق بعضها. عند فتح نموذج جديد يبقى السابق تحته، وعند إغلاق
النموذج الأعلى يعود التطبيق إلى النموذج السابق. يمكن إبقاء عدة فواتير مفتوحة
معاً. إذا احتوت فاتورة على تعديلات غير محفوظة، يطلب التطبيق تأكيداً قبل
التخلص منها. تُستعاد المسودات المحفوظة بعد تسجيل الدخول.

ليست كل الأزرار الظاهرة مكتملة. على سبيل المثال، يعرض زر الموقع وزر اعتماد
الفواتير/إرسالها إشعاراً بأن الوظيفة غير متاحة في هذه النسخة. كما أن بيانات
المنشأة وبعض خيارات المستخدمين لم تكتمل. ظهور زر في الواجهة لا يعني أن تكامل
النظام القديم قد اكتمل.

## 6. المخزون (`ItemsForm`)

يدعم نموذج المخزون حالياً:

- إنشاء الصنف وتعديله وحفظه والتراجع عن التعديل وحذفه، بحسب صلاحيات الدور.
- الاسم بالعربية والإنجليزية والاسم المختصر والمجموعة والنوع وطريقة
  الاستخدام والضريبة والملاحظات واختيار صورة للصنف.
- عدة صفوف لوحدات قابلة للبيع ضمن المجموعة. لكل صف وحدة وباركود وأسعار وقيم
  كمية/لون/مقاس خاصة به.
- إضافة رقم الصنف وحساب الأسعار والضريبة تلقائياً في نموذج الواجهة الحالي.
- إعداد **صنف سريع**: يظهر في تبويب الإضافة السريعة في الفاتورة؛ أما الصنف
  غير السريع فيُختار من البحث.
- منطقة بحث وتصنيف قابلة لتغيير الحجم بجانب قائمة النتائج.

نماذج `Item` و`UnitRow` الحالية مخصصة لشاشات التطبيق ولا تطابق بعد بنية
الجداول القديمة `tblItemGroup` و`tblItem` و`tblItemOtherData` و
`tblItemBalance`. يجب ربط قيم المعرفات المرجعية وعلاقات المجموعات والوحدات
بشكل صريح قبل استبدال التخزين الحالي بعمليات CRUD على الجداول القديمة.

## 7. الحسابات (`accountsForm`)

يدعم نموذج الحسابات البحث والاختيار، وإنشاء الحساب وتعديله وحفظه والتراجع عن
التعديل وحذفه. تشمل البيانات الاسم العربي والإنجليزي ونوع الحساب ونوع الدفع
والفرع والملاحظات والمعلومات الضريبية/الشخصية وبيانات التواصل. وتنظم المنطقة
السفلية في تبويبات:

- العنوان
- الوثائق والمستندات
- وسائل التواصل

تحفظ الشاشة حالياً كائنات `Account` محلية. لم تُربط بعد كل حقول الحساب
بالأعمدة الدقيقة في `tblAccount` أو بالجداول القديمة المنفصلة للتواصل
والمستندات والفروع وأنواع الحسابات.

## 8. الفواتير (`InvoiceTypeSelectForm` و`InvoiceForm`)

تحتوي قائمة أنواع الفواتير على الأنواع الثمانية التالية:

| العربية | English |
| --- | --- |
| فاتورة شراء | Purchases Invoice |
| فاتورة إرجاع مشتريات | Purchases Return Invoice |
| فاتورة ضريبية مبسطة | Simplified Tax Invoice |
| رجيع فاتورة ضريبية مبسطة (دائن) | Simplified Tax Invoice Return |
| فاتورة تأجير | Rental Invoices |
| فاتورة رجيع تأجير | Rental Return Invoices |
| فاتورة مصاريف | Spent Invoice |
| فاتورة إرجاع مصاريف | Spent Return Invoice |

تحتوي شاشة الفاتورة على تبويبات تفاصيل الفاتورة والإضافة السريعة للأصناف
والبحث/اختيار الأصناف. يمكن استخدام قارئ الباركود في تبويب البحث؛ فعندما
يرسل القارئ رقم الباركود ثم Enter يضيف التطبيق الصنف المطابق. إذا أضيف الصنف
الموجود مسبقاً، تزداد كميته بدلاً من تكرار صفه. ويمكن تحديد عدة صفوف وحذفها
معاً.

تسجل الشاشة تاريخ ووقت الفاتورة والتسليم ورقم الفاتورة وأدوار الحسابات وحالة
الضريبة ونسبتها والملاحظات والخصم والأصناف ومبالغ الدفع. رقم الفاتورة في
التسلسل المحلي من ست خانات. يمكن كتابة مبالغ الدفع تحت خيارات الدفع؛ ويؤدي
اختيار نوع دفع واحد إلى تحويل المبلغ المتبقي إليه إذا لم يكن هناك توزيع على
أكثر من نوع. وتحسب الشاشة إجماليات السطور والفاتورة من بيانات الأصناف
الحالية.

تُحفظ الفواتير غير المكتملة كمسودات وتُستعاد بعد تسجيل الدخول. لكل فاتورة
مفتوحة حالة ومسودة مستقلتان. يقوم **حفظ** بتخزين الفاتورة محلياً ومسح سطورها
ومبالغ الدفع وتجهيز الرقم التالي. أما **حفظ وطباعة** فيحفظ الفاتورة ويعيد
تهيئة النموذج أولاً، ثم يرسل PDF إلى طابعة الفواتير المحددة. إذا فشلت
الطباعة تبقى الفاتورة محفوظة ويعرض التطبيق سبب تعذر الطباعة؛ فلا تحفظها مرة
أخرى لمجرد أن الطابعة لم تعمل.

يسمح سجل الفواتير بالبحث في الفواتير المحفوظة ويعرض إجراءات العرض والتحرير
والطباعة المتاحة. يمكن ضبط إعدادات طباعة كل نوع من الفواتير منفرداً، ومنها
مقاس الورق والاتجاه واللغة وإعدادات الإيصال الحراري. بيانات الفواتير الحالية
هي سجلات محلية لشاشات Flutter وليست سجلات في `tblInvoice` و
`tblInvoiceItem` المتحقق منهما.

## 9. طباعة الباركود

تتيح شاشة `PrintBarcodesForm` البحث عن الأصناف واختيارها، وضبط قيمة الباركود
وقالب الملصق، وإدخال بيانات الصنف والتواريخ والكمية المطلوبة للطباعة. يمكن
اختيار طابعة للباركود مستقلة عن طابعة الفواتير. يستطيع المتصفح استخدام مسار
الطباعة المعتاد، بينما يوفر رفيق سطح المكتب اكتشاف الطابعات والطباعة المحلية
بحسب دعم النظام.

## 10. إعدادات الطابعات والفواتير

يفتح خيار **إدارة → إدارة الطابعات والفواتير** نموذج إعدادات من تبويبين:

- **الطابعات:** اكتشاف الطابعات المثبتة واختيار طابعة الفواتير وطابعة
  الباركود. يستطيع رفيق سطح المكتب تزويد واجهة الويب بقائمة الطابعات المحلية.
- **الفواتير:** اختيار نوع الفاتورة ومقاس الورق، مثل A4 أو الإيصال الحراري،
  واتجاه عمودي/أفقي واللغة وأبعاد/تصميم الإيصال، ومعاينة التصميم وحفظه.

تحفظ إعدادات الطابعات والتصميم حالياً مع إعدادات التطبيق المحلية، ولا تدخل
ضمن نسخة بيانات الأعمال الاحتياطية أدناه.

## 11. رفيق الطباعة المحلي

كُتب رفيق الطباعة بـFlutter/Dart ويستخدم قائمة الطابعات المثبتة في نظام
التشغيل. يمكن تشغيله داخل وضع سطح المكتب المستقل أو ضمن رفيق الويب المحلي.
وعند استخدام الويب يوفر نقطة محلية محمية لاكتشاف الطابعات واستقبال مهام
الطباعة. يتم ضبط أصول الويب المسموح بها من خلال `PRINTER_ALLOWED_ORIGINS`،
كما تستخدم الخدمة رمز وصول. لا تعرض النقطة المحلية على شبكة عامة ولا تتجاوز
فحص الأصل أو الرمز.

يعتمد اكتشاف الطابعة على تثبيتها وإتاحتها لمستخدم نظام التشغيل الحالي. إذا لم
تظهر الطابعة، فتحقق أولاً من ظهورها في إعدادات طابعات النظام، ثم أعد تشغيل
الرفيق وأعد اكتشاف الطابعات من التطبيق.

## 12. التخزين المحلي والنسخ الاحتياطي

تحفظ شاشات التطبيق الحالية البيانات عبر Drift/SQLite. عند التهيئة تُنقل
بيانات SharedPreferences السابقة إلى مخزن SQL المحلي، وتبقى القيم القديمة
نسخة استرداد. تستخدم نسخة الويب SQLite WebAssembly والتخزين الذي يوفره
المتصفح. تحفظ الشاشات سجلاتها الحالية بصيغة التطبيق داخل جداول الإعدادات
المحلية، بما فيها المخزون والحسابات والفواتير والمسودات وإعدادات الطابعات
وتصميم الفواتير. مخطط الجداول العلائقية القديمة المنفصل لا يُثبت تلقائياً في
قاعدة التطبيق.

تتضمن نسخة JSON الاحتياطية حالياً:

- المخزون
- الحسابات
- الفواتير المحفوظة
- رقم الفاتورة التالي

لا تتضمن كلمات المرور أو الجلسات أو إعدادات الطابعة أو تصميم الفواتير. يحتوي
الملف على بيانات أعمال مقروءة؛ لذا احفظه في مكان خاص وآمن. يتحقق الاسترداد
من تنسيق الملف وبنية السجلات، ويعرض الأعداد، ثم يطلب التأكيد. عند التأكيد
تُستبدل بيانات المخزون والحسابات والفواتير المحلية وتسلسلها الحالية. لا يوجد
تراجع داخل التطبيق عن الاستبدال؛ لذا أنشئ نسخة استرداد منفصلة قبل المتابعة.
بعد الاستعادة أعد تشغيل التطبيق لتحديث الشاشات المفتوحة.

## 13. طبقة الوصول إلى البيانات (DAL)

توجد طبقة DAL المشتركة في `lib/dal/`:

1. يحفظ `LegacyModel` القيم بمفاتيح أسماء الأعمدة القديمة الدقيقة ويرفض
   الحقول غير المعروفة. لا تحول القيم تلقائياً إلى `DateTime`؛ لأن بعض
   التواريخ القديمة غير صالحة ويجب إبقاؤها كما وردت إلى أن تُراجع.
2. يحدد `LegacyDataSource` عمليات القراءة والإضافة/التحديث والحذف المشتركة.
3. يطبق `LegacyRepository<T>` بيانات النموذج والتحقق من المفتاح الأساسي.
4. يستخدم `SqliteLegacyDataSource` اتصال Drift.
5. يستخدم `SupabaseLegacyDataSource` واجهة PostgREST عبر HTTP.

يتضمن فهرس النماذج جميع تعريفات الفئات الـ357 والخصائص العامة الـ2,136،
مع ملف Dart منفصل لكل فئة. تُحفظ أسماء الفئات والخصائص وحالة الأحرف وأسماء
أنواع VB.NET الأصلية كما هي في البيانات الوصفية وملف
`migration/legacy_dal_model_catalog.json`. تُمرر القيم كبيانات خام حتى لا
تتحول المعرّفات أو الرموز المخزنة أو التواريخ القديمة غير الصالحة بصمت.

تم تأكيد ثمانية ارتباطات بين الفئات والجداول في المخطط المرفق:

| النموذج | الجدول | المفتاح الأساسي |
| --- | --- | --- |
| `ItemGroupModel` | `tblItemGroup` | `ID` |
| `ItemModel` | `tblItem` | `ID` |
| `ItemOtherDataModel` | `tblItemOtherData` | `ItemID` |
| `ItemBalanceModel` | `tblItemBalance` | `ItemID` |
| `accountModel` | `tblAccount` | `ID` |
| `tblInvoiceModel` | `tblInvoice` | `ID` |
| `tblInvoiceItemModel` | `tblInvoiceItem` | `InvoiceID` و`ID` |
| `tblMoneyTransactionModel` | `tblMoneyTransaction` | `ID` |

للنماذج الـ349 الأخرى ملفات مستقلة، لكن حالة ارتباطها بالجداول «غير محسومة»؛
ولا يتم تخمين أسماء الجداول. يتطلب كل مهايئ وجود الجداول القديمة مسبقاً،
ولا يثبت مخطط الجداول الـ357. كما أن شاشات الأعمال لا تستخدم هذه المستودعات
بعد، ولا توجد قائمة عمليات غير متصلة أو آلية لحل التعارض أو محرك مزامنة.

اختار المستخدم SQL Server ليكون قاعدة البيانات الكاملة عبر الإنترنت، لأن
PostgreSQL/Supabase لا يستطيعان حفظ ستة أسماء فهارس قديمة تتجاوز حد المعرف
البالغ 63 بايت. يستطيع عقد النماذج والمستودعات المشترك دعم مهايئ API يتصل
بـSQL Server، لكن هذا المهايئ واتصال الخادم لم يُنفذا بعد. يظل مهايئ Supabase
اختيارياً، ولا ينبغي استخدامه كمخزن كامل للنظام القديم إلا إذا وافق المستخدم
على تقصير أسماء الفهارس.

## 14. ترحيل قاعدة Access القديمة

### القيود المعروفة في المصدر

لا يكفي مخطط قاعدة البيانات وملف CSV المتاحان حتى الآن لإعلان اكتمال استيراد
سليم بلا فقد:

- يتضمن المخطط 357 جدولاً و982 فهرساً، لكنه لا يتضمن تعريفات العلاقات
  الخارجية.
- يتضمن أرشيف CSV عدد 1,544,263 صفاً، لكن الحقول الفارغة لا تميز بين
  SQL `NULL` والنص الفارغ المقصود. وترفض بعض الفهارس الفريدة تكرار النصوص
  الفارغة.
- يحتوي التصدير على 53,400 قيمة غير فارغة في
  `tblMoneyTransaction.TransactionDate` بيوم `00`. لا تطبع هذه القيم إلى
  تاريخ آخر ولا تغيرها بصمت؛ لا يستطيع `DATETIME2` في SQL Server تمثيلها
  كتاريخ صحيح.
- تحتاج خمسة أعمدة نصية طويلة مفهرسة إلى التحقق من أطوالها قبل استعمال
  مخطط SQL Server المرشح.
- يلزم ملف `.accdb` الأصلي وبياناته لحل هذه المسائل.

### التصدير والتحقق والاستيراد

على macOS/Linux يستخدم المصدّر المشترك Java 11 أو أحدث وMaven مع UCanAccess:

```sh
./scripts/migration/export_access.sh \
  --database "$HOME/path/to/legacy.accdb" \
  --output "$HOME/path/to/legacy-access-export.zip"
```

على Windows يستخدم `scripts/migration/export_access.ps1` محرك Microsoft Access
Database Engine المطابق لمعمارية عملية PowerShell. يقرأ المصدّران المصدر ولا
يعدلان سجلاته. يحتوي الناتج على بيان بالجداول والأعمدة، ويميز SQL `NULL` عن
النص الفارغ، ويحول القيم الثنائية إلى Base64.

تحقق من الأرشيف المصدر:

```sh
python3 scripts/migration/validate_legacy_csv_export.py \
  --archive "$HOME/path/to/legacy-access-export.zip" \
  --null-marker '\N' \
  --escape-prefix '\'
```

بعد نجاح التحقق الصارم فقط، أنشئ ملف SQLite محلياً جديداً:

```sh
python3 scripts/migration/import_legacy_csv.py \
  --archive "$HOME/path/to/legacy-access-export.zip" \
  --output "$HOME/path/to/CodesSystem.sqlite"
```

ينشئ المستورد قاعدة مؤقتة جديدة ولا ينشرها إلا بعد نجاح فحوصات المخطط وعدد
الصفوف والقيود والسلامة. يحفظ نص التواريخ القديمة غير الصالحة في SQLite
ويبلغ عنها. لا تستورد إلى قاعدة إنتاج ولا تستبدلها قبل تأكيد معاني القيم
الفارغة والتواريخ، وإنشاء نسخة استرداد.

فحوصات مفيدة من جذر المستودع:

```sh
python3 scripts/migration/audit_legacy_schema.py
python3 -m unittest discover -s scripts/migration -p 'test_*.py'
cd artifacts/accounting/flutter_app && flutter analyze && flutter test
```

## 15. الحالة الحالية وخطوات الاستكمال

### ما هو موجود في أساس Flutter الحالي

- إطار عربي RTL باستخدام Fluent UI وتسجيل الدخول.
- التحقق من الأدوار والصلاحيات.
- واجهة المخزون وصفوف الوحدات، وواجهة الحسابات.
- أنواع الفواتير الثمانية ونماذجها ومسوداتها وسجلها وترقيمها المحلي وخياري
  الحفظ والحفظ مع الطباعة.
- نموذج الباركود ورفيق الطباعة المحلي.
- إعدادات طباعة مستقلة لكل نوع فاتورة واختيار الطابعات.
- التخزين المحلي عبر SQLite والنسخ الاحتياطي والاستعادة.
- ملفات نماذج DAL منفصلة لجميع الفئات القديمة الـ357؛ تم تأكيد ارتباط ثمانية
  جداول، وبقيت ارتباطات النماذج الـ349 الأخرى غير محسومة صراحة.
- أساس تدقيق المخطط والتحقق من CSV والاستيراد واختبارات الترحيل.

### ما لم ينفذ أو يربط بعد

- عمليات CRUD في الشاشات على جميع الجداول القديمة الدقيقة.
- مهايئ API وخادم SQL Server ومخطط SQL Server متحقق منه.
- المزامنة بين العمل دون اتصال والعمل عبر الإنترنت وحل التعارض وبيانات
  المزامنة.
- استيراد إنتاجي من Access بعد حسم معنى الخانات الفارغة والتواريخ غير
  الصالحة.
- بقية وحدات النظام القديم وتقاريره وعمليات ZATCA وصلاحياتها.
- بعض إجراءات القوائم الظاهرة مثل إرسال/اعتماد الفواتير وبيانات المنشأة.
- اختبار شامل باستخدام قاعدة Access الحقيقية وخادم SQL Server حقيقي.

الترتيب المقترح للاستكمال: مطابقة بقية النماذج والعلاقات؛ تأكيد معاني قيم
Access؛ استكمال مخطط SQL Server والوصول عبر API؛ ربط كل مجال على حدة عبر DAL؛
إضافة المزامنة بعد نجاح CRUD واختبارات مطابقة البيانات؛ ثم ترحيل بقية الوحدات
والتقارير القديمة.
